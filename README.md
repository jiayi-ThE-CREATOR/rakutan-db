## 1. KOAN からの取得について（2026-08-13 実測で更新）

**取得できる。** 外部公開シラバスは**ログイン不要**で、共通教育科目 2026年度は **1,112件**。
詳細ページに「成績評価の内訳（%）」が構造化テーブルで入っており、これがそのまま
楽単スコアの入力になる。手順は `scrape/`（下記 8.）。

```
$ curl https://koan.osaka-u.ac.jp/robots.txt
User-agent: *
Disallow: /
```

robots.txt は全パスを disallow している。これは法律ではなく、
また対象は認証付きの学務システム全体に向けたものと思われるが、
**低頻度アクセス（既定 2 秒間隔）・1回取り切り・ローカルキャッシュ**を守ること。
急いで得られるものは何も無く、失うもの（大学からの停止要請）は大きい。

### KOAN から取れないもの

定員／レポート本数／字数／時間外学習の時間／毎回小テストの有無 ―― この5つは
シラバスに存在しない。**だから口コミ投稿の4タップで聞く**（下記 3.）。
取得と口コミは重複せず、互いの穴を埋める関係になっている。

## 2. スコアの設計（`score.py`）

### なぜ S〜F を出さないのか
1. クロバスの S〜F 評価体系は流用しない方針（著作権・不正競争）
2. それ以上に、**一文字に潰すと根拠を提示できなくなる**。数字が外れたときに
   「なぜそう出たか」を説明できないサービスは、学生の信用を一度で失う

### 4軸
| 軸 | 何を見ているか | 出典 |
|---|---|---|
| 試験 | 期末試験の成績比率、持込可否 | 成績評価の方法・基準 |
| レポート・課題 | 本数・分量・時間外学習の指示時間 | 同上＋授業時間外学習 |
| 出席拘束 | 出席点比率、毎回の小テスト・リアぺ | 同上 |
| 規模・形態 | 定員、講義／演習／集中講義 | 時間割・授業形態 |

すべて 0〜100 で **高いほど負荷が軽い**。

### 重みは固定しない
固定重みだと壊れる。例：**レポート1本12,000字・試験なし・出席なし** の科目は、
試験軸と出席軸が満点になるので総合が「軽め」に出る。実際は激重。

そこで 試験／レポート／出席 の重みを、その科目の**成績評価の内訳から動的に配分**する
（floor 10% ＋ 評価比率に応じて 58% を配分、規模軸は固定 12%）。
成績の100%がレポートの科目は、レポート軸で 68% 判定される。

会議メモの「テスト形式とレポート形式を分ける／レポートが激重の可能性あり」は
この形で実装に入っている。

### 当てはめられない情報の扱い
「先生がお爺さん」「板書が読めない」のような、ロジックに乗らない情報は
`tags` に入れて**表示だけする。スコアには一切入れない**。
数値の根拠を100%提示できる状態を守るため。

### 信頼度
6つの事実項目のうち何個埋まっているかで `high / mid / low`。
low の科目は総合値を出しても「参考値」としか表示せず、
未取得の項目名を画面に列挙する。**欠損を平均値で埋めない。**

## 3. 口コミと楽単スコアの関係

別物ではあるが、**入力経路は1本にできる**。

投稿フォームを自由記述だけにせず、
「成績評価は？（試験◯% / レポート◯% / 出席◯%）」「レポートは何本・何字？」
「毎回リアぺある？」を**構造化された選択式で聞く**と、
その回答がそのままスコアの入力になる。

- スコア = 構造化された事実の集計（数値・根拠提示可）
- 口コミ = 自由記述とタグ（表示のみ・スコア非算入）

KOAN が引けない以上、この設計にしておくと1本の投稿導線で両方が貯まる。

## 4. API-first

画面は `/api/courses` を叩いているだけ。LINE Bot も同じ API を使う。

> **Custom GPT は不採用（2026/8/11 決定）。** ChatGPT アカウントが必要になる時点で
> 「ログイン不要で今すぐ引ける」という我々の一番の強みと矛盾する。入口は LINE に一本化する。
> API-first の設計自体はそのまま有効 ―― 使うのが GPT ではなく LINE に変わるだけ。

| エンドポイント | 用途 |
|---|---|
| `GET /api/courses` | 検索。`q` `category` `campus` `term` `day` `period` `min_confidence` `sort` |
| `GET /api/courses/{id}` | 1件＋算出根拠 |
| `GET /api/meta` | フィルタ用の選択肢、重みモデル |
| `GET /api/openapi.json` | API仕様書。LINE 側や外部クライアントが読む |
| `GET /api/health` | 死活とデータ件数 |

```bash
curl 'http://localhost:8000/api/courses?q=統計&sort=rakutan'
curl 'http://localhost:8000/api/courses?day=月&period=1'
```

CORS は `*` で開けてある（プロトタイプのため。本番では絞る）。

### LINE について
会議メモにある `line-harness-oss`（Lステップ無料版）を使うにしても、
**リッチメニューの各項目が最終的に叩くのはこの API**。
なので LINE を先に作るか Web を先に作るかは順序の問題であって、
API を先に切っておけばどちらからでも生やせる ―― という 8/7 の判断がそのまま効いている。

## 5. 意図的にスコープに入れていないもの

| 項目 | 理由 |
|---|---|
| **過去問** | 阪大は過去問の流出に厳しい可能性があるという会議メモの指摘どおり。著作権は作問者（＝教員）にあり、無断掲載は「大学からの停止要請」の最短ルート。**このプロジェクトを一夜で終わらせうる唯一のリスクに自分から触りにいかない**。やるなら別サービス・別法人格で、教員の許諾を取った上で |
| 決済 | Phase 3 では作らない（3月に判断するオプション） |
| インターン・カフェ情報などのオールインワン化 | v1 は楽単のみ。開発1〜2名で守れるスコープは「検索・スコア・投稿」の3つだけ |
| **教員名を評価の軸にすること** | 下記のとおり、名前は事実として載せるが、教員を単位にした集計・並び替え・検索は作らない |

---

### 教員名の扱い（2026/8/15 確定）

以前この章には「教員名はサンプルにも入れていない」と書いてあり、`CLAUDE.md` の
「担当教員名はシラバスの事実として載せる」と矛盾していた（政岡さんの指摘）。
**`CLAUDE.md` 側に統一する。載せる。**

載せる理由は、無いと**サービスが成立しないから**。
「基礎解析学I」は10コマ以上あり、曜限も担当教員も違う。履修登録で選ぶのは
科目ではなくコマなので、教員名が無いと学生は自分が登録すべき行を特定できない。
名前自体は KOAN の外部公開シラバス（ログイン不要）に載っている事実でもある。

危ないのは名前ではなく、**名前を評価の単位にすること**。よって3つを禁じる。

1. **教員を軸にした集計・並び替え・検索を作らない**
   「教員別の楽単ランキング」「この先生の他の科目」は作らない。
   事実の並記が「この教員は楽」という評価に変わるのはこの瞬間
2. **口コミの自由記述に教員個人への言及を書かせない**
   投稿ガイドラインに明記し、投稿前の注意書きに出す。
   評価の対象は科目であって人ではない
3. **スコアの見出しの隣に教員名を置かない**
   教員名はシラバスの事実ブロック（曜限・単位数・評価内訳）の中に置く

この3つを外すなら、それは別の判断なので `CLAUDE.md` と併せて書き換えること。

### 変更を「見える」ようにする3つの仕組み

**① Discord への自動通知** ―― 誰が何を変えたかが、書かなくても流れる。設定は Discord 側で：

1. Discord の該当チャンネル → 編集 → 連携サービス → ウェブフックを作成 → URL をコピー
2. その URL の末尾に **`/github`** を足す
3. GitHub の Settings → Webhooks → Add webhook にそれを貼る（Content type は `application/json`）
4. 送るイベントは Pushes / Pull requests / Issues の3つで十分

**② スクショ差分** ―― PR を出すと GitHub Actions が主要5画面を撮って before/after を並べる
（`.github/workflows/screenshots.yml`）。**コードが読めなくても画像で参加できる**のが狙い。
とくにスマホ表示は全員で見る。

**③ 進捗ダッシュボード** ―― `/progress.html`（ローカル専用）

```bash
python3 server.py     # → http://localhost:8000/progress.html
```

コードに現れない仕事（口コミ収集・LINE・拡散）も含めて、**誰が・どこまで・いつ更新したか**が1画面で分かる。
自分の行は `data/progress.json` の `done` / `note` / `updated` を書き換えて push するだけ。
なお実体は `tools/progress.html` に置いてある（`web/` に入れると公開されてしまうため）。
URL は変わらないので使い方は同じ。
科目数と評価割合の充足率だけは `courses.json` から自動集計されるので手で書いても上書きされる。

### 引き継ぎルール（直列タスク）

**自分のタスクが終わったら、次の人に渡す前に必ず4項目を書く。**

1. 何が動く状態か（コマンド1行で再現できる形で）
2. 何をしていないか（既知の穴・未確認のこと）
3. 次の人が最初に打つコマンド
4. 踏んだ罠

Discord に投稿し、同じ内容を `HANDOFF.md` の先頭に追記して push する。
**口頭の説明はメモを書いた上で行う** ―― 渡す相手は移動中や深夜に詰まる。
そのとき開けるのは文字だけ。

見本は `HANDOFF.md` の「① スクレイパ v0」の項。

### ブランチ

```
main                    常に動く状態を保つ
feat/<名前>-<内容>       例: feat/matsushita-mobile
```

`main` に直接 push しない。PR を出すとスクショが撮られ、Discord に流れる。

## 8. スクレイパ（`scrape/`）

```bash
python3 scrape/fetch.py --limit 10   # まず10件で動作確認
python3 scrape/fetch.py              # 全件（1,112件・delay 2秒で約45分）
python3 scrape/parse.py              # data/courses.json を作る
python3 server.py                    # courses.json があればそれを読む
```

**取得（fetch）と解析（parse）は分けてある。** 抽出ロジックは必ず直すことになるが、
HTMLがローカルにあれば parse は何度でもやり直せて、KOAN を叩き直さずに済む。
`fetch.py` は保存済みを飛ばすので、中断しても再実行で続きから。

`--delay` の既定値 2 秒は短くしないこと。急いで得られるものは何も無く、
失うものは大きい。

### 引き継ぎポイント（v0 → 全件）

| 状態 | 内容 |
|---|---|
| 動作確認済み | 検索・ページング・詳細取得・成績評価テーブルの解析（10件で 100%） |
| **未確認** | **1,112件での充足率。10件は同じページの先頭なので偏っている可能性がある** |
| 要拡張 | `METHOD_RULES` ―― 評価方法は固定語彙ではない（「態度（積極性や協調性等）」「Class debate」等が実在）。未知の名前は parse.py が最後に一覧で出すので、それを見て足す |
| 取れない | 定員／レポート本数／字数 ―― KOANに存在しない。**口コミ投稿の4タップで聞く** |
| 空になりがち | 持込可否・時間外学習の時間 ―― 本文中の書き方が一定でない |

同じ科目名が複数出るのは正常（複数コマ開講）。時間割コードが違えば別レコード。
