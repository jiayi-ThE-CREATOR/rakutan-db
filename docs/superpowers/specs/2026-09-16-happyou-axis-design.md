# 発表を独立した軸にする

2026-09-16 ｜ 状態: 設計ずみ・未実装 ｜ 前提: #128（試験ルールから裸の「期末」「中間」を外す）マージ済み

## 何をするか

いま「発表」は `METHOD_RULES` で **report バケツ**に入っている。これを独立した
`presentation` バケツにし、採点でも独立した軸として扱う。

これは採点の作り直し（相性度への一本化）の最初の一歩で、全体は3段に分けている:

1. **発表の分離**（この文書）
2. **採点エンジンの作り直し** ―― 重みを科目の内訳ではなく学生から取る固定重み（相性度）、試験の有無の落差、規模軸の削除、事実層:体感層＝8:2
3. **好みを調整する UI** ―― 結果カードからの一押しで重みを変える。LINE ゲート（#139）の扱い次第

発表を先に分けるのは、2 の既定の重みに「発表」が入るため。

## なぜ今の動的重みのまま軸を足すのか（決定の経緯）

採点エンジンを作り直すまでのあいだ、発表をどう採点するかは3案あった:

| 案 | 内容 | 結論 |
|---|---|---|
| A | データだけ分け、採点は作り直しまでレポート扱い（点数は動かない） | 不採用 |
| **B** | **いまのエンジンのまま発表を独立した軸にする** | **採用** |
| C | 発表の分離と採点エンジンの作り直しを1つにまとめる | 不採用 |

wang が B を選んだ。ただし B を**そのまま**入れると分布が崩れることを実測で確認した:

    発表軸の式            点数が動いた科目   平坦な閾値での最大 band
    比例のみ ×0.45        7,479 / 7,482      63.2%
    P=15 + ×0.30          7,461              66.2%
    P=30 + ×0.25          7,436              72.9%

発表を持つ科目は 2,530 件しかないのに、ほぼ全科目の点数が動いている。原因は式ではなく
**動的重みの保底（`AXIS_FLOOR = 0.10`）**。保底は内訳に出てこない軸にも付くので、
新しい発表軸は「発表が無い約5,000科目」で満点 100 × 0.10 を足し、全科目を機械的に
押し上げて1か所に寄せる（2026-09-03 に小テスト軸を足したときに記録された現象と同じ）。

この結果を見たうえで、wang は **B を維持し、保底の付け方を変える**ことを選んだ（2回選び直して確定）。

## 決定

### 1. 振り分け：発表ルールの行き先だけを変える

    (r"発表|プレゼン|presentation|leading", "report")   →   "presentation"

**ルールの順序は動かさない。** 発表ルールはレポートのルールより後ろにあるので:

- 「発表」「最終発表」「グループ発表」「Pair presentations」など**発表だけの項目**が移る
- 「個人のレポートとプレゼンテーション」「レジュメと発表」のような**レポートと同居する複合項目**は、
  先に当たるレポートのルールに残る（既存の分類を黙って動かさない）
- 「口頭試問」（203箇所）は試験ルールが先に当たるので **exam のまま**
- 「その他（レポート、課題提出、小テスト、発表、学習への参加度）」（120件）は
  小テストのルールが先に当たる既知の問題で、今回は触らない

実測（全 7,906件）: **発表バケツを持つ科目 2,530件**。発表らしい項目名は 186種・延べ 3,128箇所で、
いまの行き先は report 2,741 / exam 220 / quiz 122 / 未分類 38 / attendance 7。

### 2. 採点：発表軸

    発表が内訳に無い（0%）    → 100（「発表なし」）
    発表がある               → 100 − (30 + 比率 × 0.25)

内訳そのものが読めない科目（`eval_ratio` が None）は None。キーが無いのは「0%」で
「不明」ではない（出席・小テスト・レポート軸と同じ扱い）。

固定罰点 30 は「発表があること自体の負担」。人前に立つ・日程が動かせない・グループなら
調整が要る、というレポートとは違う性質の重さを表す。

### 3. 動的重みの保底：内訳に出てくる軸だけに付ける

    現行:  w[k] = 0.10 + 0.48 × share[k]              （全軸に保底）
    変更:  w[k] = 0.10 + 0.48 × share[k]  if share[k] > 0  else 0
           出てくる軸の w を合計 0.88 に正規化し、規模・形態に 0.12

- 内訳に出てこない軸は重み 0 になり、その軸の値（多くは満点 100）が総合値に混ざらない
- 出てくる軸だけで 0.88 に正規化するので、**`weight_sum` がそのまま「算出できた割合」
  という意味は変わらない**。`COVERAGE_MIN = 0.60` の判定もそのまま使える
  （正規化しないと、レポート100%だけの科目は重みの合計が 0.48 になり、`COVERAGE_MIN` を
  割って大量に「情報不足」へ落ちる）
- 内訳の合計が 0 の科目（読めない）は、5軸に 0.88 を均等に配る。この科目は `eval_ratio` が
  読めないので各軸の値が None になり、重みの配り方は総合値に影響しない

### 4. band 閾値

P（発表の固定罰点）ごとに、±1 動かしても 1.5pt 以下しか動かない平らな場所から、
4つの band が最も均等になる3点を選んだ。`band_of` で実際に数えた最大 band:

| P | 閾値 L/N/H | テスト⑧が見る最大 band | 発表のみ / レポートのみ 中央値 |
|---|---|---|---|
| 20 | 84 / 76 / 69 | 29.2% | 55 / 55 ← 分けた意味が無い |
| 25 | 83 / 72 / 30 | **42.5%** ← 地形が崩れる | 50 / 55 |
| **30** | **83 / 77 / 69** | **31.0%** | **45 / 55** |
| 35 | 83 / 76 / 69 | 30.0% | 40 / 55（出席のみ 45 より重い） |

**P=30・閾値 83/77/69 を採る。** 守衛（35%）まで 4pt の余裕があり、発表がレポートより
重く出る。

🚨 **P=25 だけ崩れるように、地形は単調ではない。** 閾値は実装時に同じ手順で必ず測り直し、
この表の値をそのまま写さないこと。

### 5. 画面

- **配点スライダーに「発表」を足す**。スライダーは `CAP_AXES` のループで作られている
  （`web/assets/app.js` の `$("#sliders").innerHTML = CAP_AXES.map(...)`）ので、
  キーの追加で済む
- **条件チップ「レポートのみ」の定義に「発表が 0%」を足す**
- **条件チップ「発表なし」を新設**（「小テストなし」の直後。チップの並びは `CONDITIONS` の挿入順）
- 軸の表示名 `AXIS_LABEL["presentation"] = "発表の少なさ"`

実測したチップ件数（`server.CONDITIONS` の判定そのもので数えた）:

    出席なし      2,176 → 2,176   抜けた 0
    レポートのみ    508 →   298   抜けた 210（発表を含む科目。意図した変化）
    持ち込み可       18 →    18   抜けた 0
    1限以外       6,979 → 6,979   抜けた 0
    集中講義        193 →   193   抜けた 0
    小テストなし  5,953 → 5,953   抜けた 0
    口コミあり      141 →   141   抜けた 0
    発表なし     （新設）→ 5,004

🚨 **`CAP_AXES` に `presentation` を入れ忘れると「発表なし」が全 7,906件に一致する（実測）。**
`passes_caps`（Python）も `passesCaps`（JS）も、最初に「`CAP_AXES` の上限が全部 100% なら
通す」と判定するので、`CAP_AXES` に無いキーの上限は**黙って無視される**。エラーにも
ならず、チップを押しても何も絞られないだけ。テストで固定する。

### 6. LINE

`PRESETS` の各プリセットに `presentation` を足し、値は同じプリセットの `report` と同じにする。

実測: この文書の設定一式（振り分け・発表軸・保底・閾値）で `build.py` の `rank_presets()` を
回すと、**`preset_top` の6組はすべて不変**（入れ替わり 0、順序も同じ）。LINE 側への影響は無い。

           情報不足 272 / 判定不可 152 / 参考値 89 / 軽め 1
    判定できた科目 7,482（情報不足・判定不可の件数は変わらない）
    点数が動いた科目 7,302

## 代償（wang に説明済み）

- **約 7,300 科目の点数が動く。** 採点エンジンの作り直し（固定重み）でもう一度全部動く
- **「試験のみ」と「レポートのみ」の倒挂が広がる。** 保底を外すと、成分が1つしか無い科目の
  総合値はその軸の値そのものになる:

      現在（本番）:    試験のみ 90.1 ／ レポートのみ 66.5   差 23.6
      この変更の後:    試験のみ 85.0 ／ レポートのみ 55.0   差 30.0

  方針は「多くの学生は試験を嫌い、レポートのほうがまし」なので逆向き。直すのは採点エンジンの
  作り直し（試験軸に有無の落差を入れる）。動的重みのまま試験軸だけ直す案は、分布が崩れることを
  実測で確認済み（2026-09-15）

## やらないこと

- 採点エンジンの作り直しの内容（固定重み・相性度への一本化・試験の有無の落差・規模軸の削除・事実層と体感層 8:2）
- グループ発表の加点 ―― 読める項目名は 13種・延べ 41箇所しかない
- 複合項目（「その他（A、B、C）」型）を複数バケツへ按分する仕組み
- 口コミフォームに発表の項目を足すこと
