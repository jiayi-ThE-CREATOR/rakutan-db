# レポート軸を「割合で形を測る」方式に戻す

2026-09-11 ｜ 状態: 設計ずみ・未実装

## 何が問題か

判定が出ていない科目が半分以上ある。実測（`web/data/courses.built.json` 全 7,906 件）:

```
情報不足  4,121   判定不可  147
拘束は軽い 2,604   やや重め   461   標準 443   軽め 46   重め 45   参考値 39
```

**54% の科目に点数が無く、点数が出た 3,638 件のうち 2,604 件（72%）が同じ「拘束は軽い」を
表示している。** 現状このサイトは科目を分別できていない。

原因は `score.py` の `_report_load` にある。`report_count` / `report_words` /
`out_of_class_hours` のどれも無い科目では `None` を返すが、その3つは実測でこれだけしか
埋まっていない:

```
report_count 非None:          0 / 7,906   ← 一件も無い
report_words 非None:          3 / 7,906
out_of_class_hours 非None:  149 / 7,906
→ レポート軸が None:      7,754 / 7,906   （98%）
```

3つともシラバスの詳細ページから取る値だが、`data/raw/detail` はこの環境に 10 件しか無い
（`data/raw` は gitignore。全件は取得した人の手元にしかない）。つまり**レポート軸は
全科目の 98% で動いていない**。軸が1本死ぬと `weight_sum` が `COVERAGE_MIN` を割り、
科目ごと「情報不足」に落ちる ―― これが 4,121 件の正体。

## 2026-08-14 の決定を読み直す

当時の記録（`_report_load` の docstring）:

> ここを ratio だけで算出していたため、成績の80%がレポートの科目に
> 「レポート軸88＝軽い」が付いていた。間違う方向が「重い科目を軽いと言う」側なので、
> 算出せず None を返す。

当時の式は `ease = 100 − ratio × 0.15` なので、80% でも 12 点しか引かれず 88 点になる。
**誤りは「ratio を使ったこと」ではなく「係数 0.15 が小さすぎたこと」だった。**
係数 0.45 なら 80% → 64 点「標準」で妥当な値になる。

軸ごと `None` にしたのは、標定の問題に対して軸の廃止で答えたことになる。その代償が
今日の 98% である。

非対称もある。**試験軸は今も `ratio × 0.15` で「形」だけを測っており、難しさは口コミ待ちに
している。** レポート軸だけが「量が測れないなら何も言わない」という別の基準で動いている。
両方とも「まず形を測り、量と難度は後から来るデータで補う」に揃えるのが筋が通る。

なお `feat/eval-hosoku` は「％を機械で拾って表に足すことはしない ―― 拾い方を決めた時点で
シラバスに無い解釈を足すことになる」と決めている。本文から本数・字数を正規表現で
取りにいく案はこの決定と衝突するので採らない。

## 決定

レポート軸は **成績評価に占める割合で「形」を測る**。量（本数・字数・時間外学習）が
取れている科目では、これまで通りそのぶんを加算する ―― 分岐は残すので、詳細ページを
全件取得した日に式を書き換えずに精度が上がる。

## やらないこと（次の spec）

このドキュメントは配点の構造には触れない。以下は別立てで扱う:

- 相性度への一本化（`dynamic_weights` の廃止、固定＝学生側の重みへ）
- **発表を独立軸にする** ―― 発表系の項目を持つ科目は 2,893 件（37%）、成績に占める割合の
  中央値は 40%、100% の科目が 68 件。いまは report バケツに同居している
- 試験軸に「有無の落差」（固定罰点 P）を入れる
- `_scale_ease` の削除 ―― 実測で**全 7,906 件が `None`** の死に軸
  （`capacity` は全件 None、「集中」は `class_format` ではなく `term` にあり、
  `SIGNAL` の `"演習"` は実データの `"演習科目"` と一致しない）
- 詳細ページの全件取得

## 実装

`score.py` の `_report_load` のみ:

- `eval_ratio` そのものが読めない科目は `None` のまま（現行どおり）
- `ratio` が読めたら `load = ratio × K` から始める
- `report_count` / `report_words` / `out_of_class_hours` があれば従来の加算を足す
- `K` の初期値は **0.45**

evidence の文言に「本数・分量は取得できていないため、形のみで判定」と明記する。

## 実測（K 別・他の軸と現行閾値はそのまま）

判定できた件数はどの K でも同じ **7,474 件**（情報不足 280 / 判定不可 152）。
K が変えるのは目盛りであって、判定できるかどうかではない。

| K | 中央値 | p10 | p25 | p75 | p90 |
|---|---|---|---|---|---|
| 0.30 | 82.3 | 73.8 | 79.1 | 86.4 | 90.2 |
| **0.45** | **78.2** | **66.5** | **74.9** | **85.0** | **89.6** |
| 0.60 | 74.9 | 55.4 | 69.7 | 84.1 | 89.0 |

判定できる科目は **3,638 → 7,474 件（46% → 95%）**。

## band 閾値の再フィット（必須・同じ PR 内で）

`LIGHT_MIN 79 / NORMAL_MIN 67 / HEAVYISH_MIN 53` は **4,121 件が判定不能だった分布の上で
決めた値**なので、7,474 件の分布ではそのまま使えない。K と同時に決める。

手順は 2026-09-03 のものを踏襲する:

1. 実測分布で位置を出す
2. 最も近い整数を採る。**切り上げない**（分布が滑らかでなく、1 動かすと大きく跳ぶ）
3. 同じ入力の科目が固まっている点（例:「出席・平常点が100%」だけの科目群）の**上**に
   閾値を置かない
4. `tools/test_haiten_filter.py` の band 分布チェックを通す

## 同期が必要な箇所

- `web/assets/app.js` の `matchLocal()` ―― score.py と同じ計算を持っている
  （「片方だけ直さないこと」とコメントに3か所書かれている）
- `server.py`
- `build.py --rescore` で `web/data/courses.built.json` を焼き直す

## テスト

- 既存の `tools/test_haiten_filter.py` を通す
- 追加: レポート比率だけが違う2件で ease が単調に下がること
- 追加: `report_count` がある科目で従来の加算が効くこと（分岐の回帰防止）
- 追加: 情報不足の件数が 280 前後に収まること（4,121 に戻る回帰の検知）

## 既知の穴

- **形しか測っていない。**「レポート40%」が 1 本 2,000 字なのか 5 本 1 万字なのかは
  区別できない。カードの evidence にそう書いて、断言しない。
- `feat/eval-hosoku`（表が空の 137 件）とは対象が重ならないが、両方入ると
  `eval_captured` が変わる科目がある。マージ順に注意。
