# 配点でしぼる ―― 設計（スペック）

> このファイルは**設計**。実装手順は同日付の `-plan.md` を見ること。
> 実装は `feat/haiten-filter`（`main` から分岐）で行い、`main` には触らない。
> **同日付の `2026-09-03-naiyou-tag-design.md`（内容タグ）とは別の PR。** 相互依存は無い。

**ゴール：** 右のスライダーを「あなたがどれだけ気にするか（0〜5の重み）」から
**「その配点が何%以下の科目を出すか（0〜100%の上限）」** に変える。
学生が言うのは「出席が重い授業はイヤ」であって「出席を重み4で評価したい」ではない。

**きっかけ：** wangさんの指摘（2026-09-03）。
「出席の緩さ 4」の 4 が何なのか誰にも説明できない。
シラバスに書いてあるのは **成績評価の内訳（%）** という具体的な数字なのだから、
画面にもその数字を出すべきである。

## 1. 調べて分かったこと（設計の前提。ここを疑うなら調べ直しから）

### ① 小テストの配点は、すでに全件で算出されている

`scrape/parse.py:36` の `METHOD_RULES` には最初から `quiz` バケツがある。
ところが `parse.py:151` で

```python
buckets["attendance"] += buckets.pop("quiz")
```

と**出席へ足し込んで捨てている**。この1行を消すだけで4本目の比率が手に入る。
**KOAN を取り直す必要は無い。**

実測（`web/data/courses.built.json` 7,906件、`eval_raw` から再計算）:

| 小テスト配点 | 0% | 1-20% | 21-40% | 41-60% | 61-80% | 81-100% |
|---|---|---|---|---|---|---|
| 件数 | 6,473 | 648 | 560 | 147 | 35 | 43 |

4軸とも分布に十分な幅がある（＝スライダーが意味を持つ）:

| 配点 | 0% | 1-20% | 21-40% | 41-60% | 61-80% | 81-100% |
|---|---|---|---|---|---|---|
| 出席（分離後） | 2,501 | 1,701 | 1,829 | 1,281 | 223 | 371 |
| 期末テスト | 4,236 | 202 | 529 | 1,089 | 1,176 | 674 |
| レポート | 2,924 | 623 | 1,052 | 1,599 | 1,064 | 644 |

### ② スライダーの意味が「重み」から「上限」に変わると、並び順の入力が消える

いまのスライダーは `score.py:match()` の内積 `Σ(重み × 軸スコア)` に入っている。
上限フィルタは科目を**落とす**だけなので、内積に渡す値が無くなる。

→ **上限は絞り込み、順位は楽単スコア。役割を分ける。**

ただし**既定の並びの第1キーは `needs_review` のまま動かさない**。
`app.js:806` の `byFit` は「テストの難しさが確認できているか」を最初に見ている。
これを外すと、誰も難しさを確かめていない一発試験の科目が最上位に戻る
（2026-08-26 実測：おすすめ上位 371件が全部それだった）。

新しい既定の並び:

```
1. needs_review が false（＝難しさが確認ずみ）を先に
2. rakutan.overall が算出できている科目を先に
3. rakutan.overall の高い順
```

`server.py:search()` と `build.py` も同じ順序にすること（既存コメントに同じ注意書きがある）。

### ③ 上限を4本とも下げると 0 件になる（※実装時に条件が1つ増えた）

成績評価の内訳は合計 100% なので、4本の上限の合計が 100 を下回れば
条件を満たす科目はほぼ存在しない。これは実装ミスではなく仕様の性質なので、
**画面で先に言う**（下記 3-④）。

> **2026-09-03 実装時の訂正。** 「原理的に存在しない」は言い過ぎだった。
> 内訳の合計が 100% に届いていない科目 ―― デンマーク語V〜VIIの6件は
> `eval_raw` が「試験20%」しか無い ―― は、4本を20%にしても通り抜ける。
> `eval_unclassified` は空なので「振り分けられている」の判定では弾けない。
>
> 対処: `passes_caps` に **内訳の合計が `EVAL_TOTAL_MIN`(80) 以上** という
> 条件を足した（`score()` が総合値を出す条件と同じ線）。これで実測 0 件になる。
> 残り80%に何が入るか分からない科目を通すのは、そもそも「証明できるものだけ
> 通す」に反していた。

### ④ 配点が最後まで読めない科目が 566 件ある

| | 件数 |
|---|---|
| `eval_ratio` そのものが無い | 152 |
| `eval_unclassified` が残っている（振り分けられなかった項目がある） | 414 |
| 内訳の合計が `EVAL_TOTAL_MIN`(80%) に届かない（③の訂正で追加） | 数十件 |
| **上限判定に使える科目** | 約 7,330 / 7,906 |

`eval_unclassified` が残る科目は「残りの %」にどの軸が隠れているか分からない。
`app.js:693` の `evalKnown` が既に同じ理由で「出席なし」チップから外している。

→ **スライダーを 100% から少しでも動かした時点で、この 566 件は結果から外す。**
「証明できるものだけ通す」。ズレを「実際より楽に見える」方向に出さないのは
`score.py` の `EVAL_TOTAL_MIN` と同じ判断。

### ⑤ 現行チップ3つはスライダーの 0% と同義になる（ただし件数は動く）

| 現行チップ | 新スライダーでの表現 | 変更前 | 変更後 |
|---|---|---|---|
| 出席なし | 出席・平常点 0% | 1,536 | **2,170** |
| 小テストなし | 小テスト 0% | 6,453 | **5,939** |
| レポートのみ | 期末0＋出席0＋小テスト0 | 482 | **482（集合ごと一致）** |

（数字は実装後の実測。設計時に書いていた 1,333 / 5,360 / 367 は
画面のスクリーンショットから拾った別のフィルタ状態の値で、誤りだった）

**出席なしが +845 件になるのは意図した変更。** いまの `CONDITIONS["出席なし"]` は
`!eval_ratio.attendance && !weekly_quiz` で、毎回小テストがある科目を出席側で弾いている。
小テストが独立した軸になれば、その判定は小テスト側の仕事になる。
（小テストが要る人は 小テスト 0% を併せて指定すればよい ―― 組み合わせで表せる）

残る `持ち込み可` `1限以外` `集中講義` `口コミあり` は配点ではないので**チップのまま**。

### ⑥ preset 4つは LINE 公式アカウントの推薦の骨格になっている

| 場所 | 使われ方 |
|---|---|
| `score.py:PRESETS` | 名前と重みの正本 |
| `build.py:rank_presets()` | 「学年 × プリセット名 → TOP100件ID」を `preset_top` に焼く |
| `worker/index.js:212` `buildRecommendation()` | `preset_top` を引いて LINE に返す |
| `worker/index.js:392` `presetQuestionMessage()` | 「何を優先する？」のクイックリプライ4つ |

memory の通り**入口は LINE 一本**なので、preset を web から消すだけでは済まない。
上限モデルに移すと `とにかく軽い` は ③ の理由で**成立しなくなる**（4本とも低い＝0件）。

## 2. 決めたこと

### ① スライダー＝上限フィルタ。4本（出席率／期末テスト／小テスト／レポート）

- 目盛りは 0〜100 の **10% 刻み**。右の数字は `30%` のように % を付けて出す

  > **5%刻みも検討したが 10 で確定（2026-09-04 wangさんの判断）。** 実測:
  > 配点の値の 7.1%（のべ1,100個）は「5の倍数だが10の倍数でない」もので、
  > 10の倍数でない配点を持つ科目は **708件＝9.0%**（出席35%の科目は90件）。
  > 5刻みで増える件数は低いほうに偏る ―― 出席の上限15%で+134件、25%で+108件、
  > 35%以上は +42/+16/+7 とほとんど効かない。
  > つまみが11段か21段かの差より、11段で迷わず動かせるほうを採った。
  > **上限は「以下」なので、35%の科目が消えるわけではない**（上限40%で入る）。
  > 拾えないのは「35%ちょうどで切りたい」という指定のほうだけ。
  > 刻みは `app.js` の `CAP_STEP` が正本。
- 既定値は**全部 100%（＝制限なし）**。触っていない状態で件数が減ってはいけない
- ラベルは学生の言葉にする（`score.py` の `AXIS_LABEL` と同じ原則）

| 内部キー | 画面のラベル |
|---|---|
| `attendance` | 出席・平常点 |
| `exam` | 期末テスト |
| `quiz` | 小テスト |
| `report` | レポート |

判定式（`c` は科目、`cap` は4本の上限）:

```
すべての軸 k について  ratio(c, k) <= cap[k]
かつ  cap のどれかが 100 未満なら evalKnown(c) が真
```

### ② 条件チップをスライダーの**上**へ移し、押すと対応するスライダーが 0% になる

wangさんの案どおり。チップは「よく使う上限のショートカット」になる。

- `出席なし` を押す → 出席・平常点のスライダーが 0% へ動く（画面上でつまみが動く）
- `小テストなし` → 小テストが 0%
- `レポートのみ` → 期末・出席・小テストが 0%
- スライダーを手で 0% にすると、対応するチップが自動で点灯する（双方向）
- 逆にスライダーを 0% から動かすと、チップは消灯する

**チップとスライダーは同じ1つの状態を指す。** 別々に持たない。

### ③ preset は**サイトの右レールからだけ**外す。LINE はこの PR では触らない

> **2026-09-03 の方針変更（wangさん）。** LINE の作り直しは別セッションで行う。
> `score.py:PRESETS` / `build.py:rank_presets()` / `preset_top` /
> `worker/index.js` は**そのまま残す** ―― 消すと配信中の LINE が即死する。
> `PRESETS` には5軸化に合わせて `quiz` の重みだけ足した（無いと小テストが
> LINE の順位に効かない）。`tools/test_bot_flow.mjs` が通ることを確認ずみ。
>
> 以下は LINE を作り直すときの設計として残す（このPRでは未実施）:

- `build.py` は `cap_top` を焼く ―― `{学年: {軸キー: [ID,…100件]}}`。
  各軸について「その配点が 0%（無い）科目を、楽単スコア順に 100 件」
- LINE の問診は 学年 → 学部 → **「いちばんイヤなのはどれ？」**（出席／期末／小テスト／レポート）
- `handleText` の自由入力は「1年 出席なし」のような言い方を受ける

**配り済みのボタンへの対応（必須）**: リッチメニューや過去のトーク履歴に
`action=preset&preset=バイト優先` が残っている。これが来たら**エラーにせず**、
新しい問診の入口（「いちばんイヤなのはどれ？」）を返す。
`action=preset` のハンドラは消さず、この転送だけを残す。

### ④ score.py に小テストを第5軸として足す

wangさんの判断（2026-09-03）。**公開済みのスコアが動くことを承知の上での選択。**

- `AXES` に `("quiz", "小テスト", _quiz_load)` を追加
- `_attendance_load()` から `weekly_quiz` の `+25` を外す（小テスト軸へ移す）
- `dynamic_weights()` は4軸で配分する。合計を 1.0 に保つため
  **`AXIS_SHARE` を 0.58 → 0.48 に下げる**（`AXIS_FLOOR` 0.10×4 ＝ 0.40、`SCALE` 0.12）
- `AXIS_LABEL` に `"quiz": "小テストの少なさ"` を追加

**必ず実測すること**: `band`（軽め／標準／やや重め／重め／情報不足）の分布が
変更前後でどう動いたかを数え、PR の説明に貼る。
`COVERAGE_MIN`（0.60）は据え置きで始め、情報不足が跳ね上がるようなら再検討する。

> **2026-09-03 実測の結果、band のしきい値も動かすことになった（設計時に無かった項目）。**
>
> 軸を1本足すと、その軸が満点になる科目（小テストが無い6,473件）の総合値が
> 機械的に上がる。実測では **判定できた3,602件がすべて上がり、下がった科目は0件**
> （中央値 +2.7、小テストあり +6.7 / なし +1.9）。しきい値を据え置くと
> 「新しい根拠は何も無いのに軽い判定が426件増える」ことになる。
>
> 一方 **順位はほとんど動いていない**（小テストあり／なし／`weekly_quiz` の
> 3群とも、順位の中央値の移動は 0.6ポイント未満）。動いたのは目盛りのほうなので、
> 目盛りに合わせて `band_of` のしきい値を **72/55/38 → 79/67/53** に置き直した
> （「変更前と同じ割合を切る位置」を実測）。
>
> 🚨 **切り上げてはいけない。** 分布が滑らかでない。とくに **53.1 ちょうどに348件**
> （「出席・平常点100%」だけで評価される科目は入力が同一）が固まっており、
> 54 にするとその348件が一斉に「重め」へ落ちる。
>
> 見張りは `tools/test_haiten_filter.py` の band 分布チェック（許容 ±3ポイント）。

### ⑤ 焼き直しの経路 ―― `build.py --rescore`

`data/courses.json`（全所属7,906件）は gitignore で取得した人の手元にしか無い。
持っていない人が `build.py` を流すと `guard_not_fewer` が止める。
そこで `--represet` と同じ形で **`--rescore`** を足した ―― 焼き済みの
`courses.built.json` を読み、`eval_raw` から `eval_ratio` を作り直し、
`score.py` で採点し直し、`preset_top` も組み直して、同じファイルへ書き戻す。
band の分布表を変更前後で出すので、そのまま PR に貼れる。

HTML を持っている人は従来どおり
`python3 scrape/parse.py && python3 scrape/years.py && python3 build.py`。結果は同じ。

## 4. データとURL

### `eval_ratio` に `quiz` が増える

```json
"eval_ratio": {"exam": 60.0, "report": 20.0, "quiz": 20.0}
```

- 0% の軸は**キーごと落ちる**（現行どおり）。「キーが無い＝0%」。
  `attendance` が消えたのは「不明」ではなく「0%」。不明は `eval_ratio` 自体が無い場合
- `eval_captured`（合計）は分離の前後で変わらない ―― 足す先が変わるだけ

### URL パラメータ

- 新: `?cap_attendance=30&cap_quiz=0` …（0〜100 の整数、`CAP_STEP` 刻み）。
  刻みに合わない値が来たら丸める ―― つまみの位置と件数が食い違うと、
  なぜその件数なのかが画面から読めなくなる。
  **丸めに刻みを直書きしないこと** ―― `CAP_STEP` を 5 に変えた実験で、
  丸めだけ 10 のままだったため 35% が往復で 40% に化けた
- **旧 `?preset=` と `?w_*=` は受け取っても無視する。** 意味が変わったので
  機械的に読み替えると「共有したときと違う結果」を黙って出すことになる。
  無視して既定（制限なし）で開くほうが害が小さい

## 5. やらないこと

| やらないこと | 理由 |
|---|---|
| 上限を「ソフトな減点」にする | 「30%以下と言ったのに35%が出る」が説明できない。切るなら切る |
| 配点不明の566件を「たぶん通る」として残す | ズレが「実際より楽に見える」方向に出る。`EVAL_TOTAL_MIN` と同じ線 |
| `とにかく軽い` を上限の組み合わせとして残す | 4本とも低い＝0件。成立しない名前を画面に置かない |
| 上限とは別に重みスライダーも残す | つまみが8本になる。どちらか片方 |
| `?preset=` を新しい上限へ機械的に読み替える | 共有済みURLが黙って別の結果を出す |
| このPRで内容タグに触る | 別PR。`parse.py`/`build.py` は両方が触るのでコンフリクトは覚悟の上、後発が寄せる |

## 6. 検証

新規テストは既存の並びに合わせて `tools/` に置く。

- `tools/test_conditions.py` / `.mjs` ―― チップとスライダーの**双方向同期**。
  「出席なしを押す → cap_attendance が 0 になる」「0 から動かす → チップが消える」

  - 上限の合計 < 100 のとき 0 件になり、警告フラグが立つ
  - 上限が1本でも 100 未満なら `evalKnown` でない 566 件が結果に出ない
  - 全部 100% のときの件数が、フィルタ前の全件と一致する
- `tools/test_bot_flow.mjs` ―― 旧 `action=preset` の postback が
  **エラーにならず**新しい問診に落ちること
- `python3 -c "import score"` 相当の再計算を回し、`band` の分布表を PR に貼る

**Python と JS の二重実装に注意。** `score.py:match()` と `app.js:matchLocal()`、
`server.py:CONDITIONS` と `app.js:CONDITIONS` は同じ内容を両方に書く決まりになっている。
