# 学部から科目区分でしぼる ―― 設計（スペック）

> このファイルは**設計**。実装手順は同日付の `-plan.md` を見ること。
> 実装は `feat/wang-division-filter`（`main` から分岐）で行い、`main` には触らない。

**ゴール：** 学生が**自分の学部を選ぶと、自分の卒業要件にある科目区分**
（人文科学系・情報教育科目・専門基礎教育科目…）でしぼり込めるようにする。

**きっかけ：** しゅんやさんの指摘②「学部学科を選べない」（2026-08-24）。
`tools/eligibility.py`（履修対象パーサ）は同じ指摘への別の答えで、**これとは別物**。
混同しないこと ―― 下の「やらないこと」を読むこと。

---

## 1. 調べて分かったこと（設計の前提。ここを疑うなら調べ直しから）

### ① 区分の顔ぶれは全11学部で同じ。学部が変えるのは単位数だけ

CELAS の「卒業要件単位数」11ページを実測（2026-08-24）。
どの学部も**同じ14区分**が並び、違うのは各区分の必要単位数だけだった。

> 当初は「理学部を選ぶと理学部の区分が出る」という作りを想定していたが、
> **その作りは成立しない。** 区分は常に14個ある。
> 学部が決めるのは「その区分が自分に必要か、要件外か」。

### ② 学部内の学科は、必要な区分の種類が同じで、数字だけ違う

学科が複数ある学部（理・工・基礎工・医）は**学科ごとに別テーブル**になっている。
実測すると、必要な区分の集合は学科間で一致し、differ るのは数字だけだった。

| | 数学科 | 物理学科 | 化学科 | 生物科学科 |
|---|---|---|---|---|
| 専門基礎教育科目 | 25 | 25 | 25 | **24** |

→ **学部→区分の2段で足りる。** 学科の段は作らない。
数字が学科でばらつく区分は `24〜25単位` のように幅で出す。

### ③ セルの結合は「合計単位数」を意味する ―― ここを読み違えると単位事故になる

`人文科学系 / 社会科学系 / 自然科学系 / 総合型` の4行が
`rowspan="4"` で**1つのセルに結合**されている学部がある。
これは「人文6・他は要件なし」ではなく「**基盤教養教育科目から合計6単位**」の意味。

工学部・医学部ではさらに `アドヴァンスト・セミナー` を含む `rowspan="5"` になる
（＝「アドヴァンスト・セミナー＋基盤教養から合計4単位」）。

> **この構造は LLM に HTML を読ませると必ず落ちる。**
> 実際、設計中に WebFetch で読ませたところ、外国語学部で
> 「人文6・社会/自然/総合は表記なし」と出た（正しくは4区分で合計6）。
> **要件表は必ず HTML を機械的にパースして取り込む。目視転記も禁止。**

### ④ 科目側に区分の欄は無い。ただし大半は既存データから推定できる

KOAN 詳細ページに「科目区分」という欄は無い。`category` は全件
`全学教育推進機構`（開設機構）で、絞り込みには使えない。
一方で**科目名の接頭辞とナンバリング**に手掛かりがある（次章）。

### 2.2 `data/faculty_requirements.json`（新規・wang 担当）

`tools/fetch_requirements.py` が CELAS の11ページから生成する。**手で書かない。**

```json
{
  "_meta": {
    "source": "CELAS 卒業要件単位数",
    "base_url": "https://www.celas.osaka-u.ac.jp/education/prerequisite/",
    "fetched": "2026-08-24"
  },
  "divisions": [ { "key": "tobira", "label": "学問への扉", "group": "教養教育系科目" }, … ],
  "faculties": [
    {
      "key": "science",
      "label": "理学部",
      "departments": ["数学科", "物理学科", "化学科", "生物科学科"],
      "requirements": [
        { "divisions": ["tobira"], "values": ["2", "2", "2", "2"] },
        { "divisions": ["kiban_jinbun", "kiban_shakai", "kiban_shizen", "kiban_sogo"],
          "values": ["6", "6", "6", "6"] },
        { "divisions": ["senmon_kiso"], "values": ["25", "25", "25", "24"] }
      ],
      "notes": [
        "＊アドヴァンスト・セミナーの修得単位の取り扱いは、各学部発行の便覧等にて確認してください。",
        "＊高度教養教育科目は、全学共通教育科目のほか、各学部においても開講されています。…",
        "注１：「自然科学系」科目は、卒業要件外とする"
      ]
    }
  ]
}
```

**`requirements` の1要素＝結合セル1つ。** `divisions` が2つ以上なら「合計で」の意味。
`values` は `departments` と**同じ長さ・同じ並び**の配列（学科の無い学部は長さ1）。
各要素は**生文字列**をそのまま持つ（`"2"` / `"－"` / `"＊"` / `"＊8"`）。
数値へ丸めない ―― `＊`（便覧参照）と `－`（要件なし）と `0` は違う事実で、
潰すと画面で嘘になる。表示のときに JS 側で解釈する。

`web/data/requirements.json` へ `build.py` がコピーする（静的配信用）。
`courses.built.json` には入れない（毎回1.7MB を太らせない）。

### 2.3 科目側の新フィールド

`courses.built.json` の各科目に2つ足す。

```json
"division": "kiban_jinbun",
"division_source": "title"
```

`division_source` は `"scrape" | "title" | "numbering" | null`。
**画面の注記に使う**（推定であることを隠さない）だけでなく、
政岡さんのデータが入ったときに何が上書きされたか数えるためにも要る。

## 3. 科目→区分の推定規則（`tools/division.py`・新規）

優先順位は **scrape > title > numbering**。上位が値を持てば下位は見ない。

| 優先 | 判定材料 | 判定 | 実測 |
|---|---|---|---|
| 1 | 政岡さんの scrape フィールド（未着） | そのまま採用 | 0件（いまは無い） |
| 2 | 科目名の接頭辞 `【人文】` | `kiban_jinbun` | 92件 |
| 2 | `【社会】` | `kiban_shakai` | 78件 |
| 2 | `【自然】` | `kiban_shizen` | 39件 |
| 2 | `【総合】` | `kiban_sogo` | 82件 |
| 3 | numbering 7〜8桁目 `1Z` | `tobira` | 250件（1Z の253件から【総合】付き3件を除く）|
| 3 | `1M` | `joho` | 76件 |
| 3 | `1F` / `1G` / `1K` / `1H` | `senmon_kiso` | 302件（数学・化学・生物・図学） |
| 3 | `1V` **かつ** 科目名にスポーツ／健康系の語 | `health_sports` | 144件 |
| — | 上記以外 | **`null`（画面では「その他」）** | 49件 |

### なぜ `1V` だけ科目名の条件を足すか

`1V` の接頭辞なし179件のうち35件は
`キャリアデザインと公共哲学` `オン・キャンパス・インターンシップ` `アカデミック・リテラシー入門`
のように、**どう見ても体育の科目ではない**（高度教養教育科目の可能性が高い）。
ナンバリングだけで一律に `health_sports` へ倒すと、この35件が
「健康・スポーツ教育科目」として学生の卒業要件計算に混ざる。

だからスポーツ／健康系の語を含むものだけを採り、残りは `null` に落とす。
**見ていない値のために規則を書くと必ず外れる**（`tools/eligibility.py` と同じ判断）。
`METHOD_RULES` の「未分類が満点に化けていた」事故（2026-08-20）と同じクラスの話。

判定語（`tools/division.py` に定数として置き、テストから参照する）：
`スポーツ` `健康` `ヘルス` `運動` `体育` `フィットネス`

## 5. 画面（`app.js` が自前で差し込む）

`rail` の「学年」セクションの直後。

```
学部からさがす   学部を選ぶと、卒業要件にある区分が上に出ます
[ 学部を選ぶ ▾ ]                     ← 未選択なら14区分をそのまま並べる

── 理学部 を選んだあと ──
あなたの卒業要件にある区分
[学問への扉 2単位 (250)]
[人文科学系 基盤教養で計6単位 (92)] [社会科学系 基盤教養で計6単位 (78)]
[自然科学系 基盤教養で計6単位 (39)] [総合型 基盤教養で計6単位 (82)]
[情報教育科目 2単位 (76)] [健康・スポーツ 2単位 (144)]
[専門基礎 24〜25単位 (302)]
[第1外国語 8単位 (0)] [第2外国語 3単位 (0)] [グローバル理解 2単位 (0)]
[アドヴァンスト・セミナー 便覧で確認 (0)] [高度教養 便覧で確認 (0)] [その他 (49)]

▸ 卒業要件外の区分も表示する (1)      ← 選択外国語（－）
ⓘ 注１：「自然科学系」科目は、卒業要件外とする
```

- 区分チップは**複数選択（OR）**。`state.division` は `Set`。
- 結合セル（合計単位）は**まとめて1チップにしない。** 区分ごとにチップを出し、
  バッジを `基盤教養で計6単位` と共通表記にして「4つ合わせて6単位」を伝える。
  1つに畳むと「人文だけ見たい」ができなくなり、絞り込みとして損。
- **折りたたむかどうかは `values` の値だけで決める**（`－` と空欄なら要件外へ送る）。
  理学部の「自然科学系は卒業要件外」は結合セルの中にあり値としては `6` なので、
  自然科学系のチップは**上に残り、注記で伝わる**。注記の日本語を機械で解釈して
  チップを移動させることはしない ―― 文面が変われば外れるし、外れ方が静かすぎる。
- 単位数バッジは `values` の生文字列から作る。全学科同じなら `2単位`、
  ばらつけば `24〜25単位`、`＊` なら `便覧で確認`、`－` は要件外へ送る。
- **`notes` は必ず出す。** 「自然科学系は卒業要件外」は、区分を隠すと意味が通らない
  ―― これが「要件外を消さず折りたたむ」ことにした理由。
- 状態は **API のクエリ**（`qs()`）に載せる：`faculty=science&division=tobira&division=joho`。
  **ブラウザのアドレス欄には出さない。** いまの絞り込み（学期・学年・条件・コマ）は
  どれもアドレス欄に出していないので、ここだけ変えると挙動が揃わない。
  絞り込み全部を URL 化するのは別の仕事。
- 区分チップの件数は、**区分フィルタを掛ける前**の集合で数える。
  そうしないと1つ選んだ瞬間に他の区分が全部0件になり、次の一手が打てない
  （空きコマグリッドと同じ理由）。

## 8. やらないこと

- **学科の段は作らない。** 必要な区分の集合が学科で変わらないため（1章②）。
- **履修対象（`tools/eligibility.py`）とは混ぜない。** あちらは「自分が登録できるか」、
  こちらは「自分の卒業要件に効くか」。同じ「学部」という言葉でも別の問い。
  同じ画面に2つ出すのは、片方が育ってから考える。
- **単位数の合計・不足数の計算はしない。** 「あと何単位」を出すには履修済みの入力が要り、
  それは「ログイン不要」と衝突する。要件表は**読み物として**出すに留める。
- **要件表の数字を手で書かない。** 1章③の通り。CELAS が更新したら再取得する。
- **区分での並び替えは作らない。** 絞り込みだけ。

## 9. ロールバック

作業は `feat/wang-division-filter` のみ。`main` は無傷。
気に入らなければ `git checkout main && git branch -D feat/wang-division-filter`。
`build.py` は `division` が無くても動くよう、既存フィールドには一切触らない。
